# BPMN XML → Compact JSON Converter

## Назначение проекта

Нужно сделать локальное средство для преобразования BPMN XML-файлов в компактный JSON, пригодный для дальнейшей обработки агентом.

Целевая цепочка проекта:

```text
BPMN XML → compact JSON → Markdown description → RAG knowledge base
````

В рамках текущего проекта реализуется только первый этап:

```text
BPMN XML → compact JSON
```

Второй этап `JSON → Markdown` будет выполняться отдельно агентом со специальным скиллом.

---

## Главная цель

Получить локальный CLI-конвертер, который:

1. Принимает BPMN XML-файл.
2. Десериализует его в готовую BPMN object model.
3. Выбирает из модели информацию, важную для понимания логики процесса и его технической реализации.
4. Удаляет визуальную layout-информацию, XML-многословность и данные, не влияющие на понимание процесса.
5. Сериализует результат в стабильный компактный JSON.

Важно: цель не в том, чтобы оставить только высокоуровневый бизнес-смысл.

В JSON также должна попадать технически значимая информация, если она влияет на исполнение процесса или помогает понять, как реализованы его шаги.

Например, реализация service task, call activity, script task, business rule task, listeners, input/output mappings и другие execution-related детали могут быть критически важной информацией и не должны отбрасываться только потому, что они технические.

Удаляем не техническую информацию, а бесполезную информацию.

---

## Технологический выбор

Использовать:

```text
TypeScript
Node.js
bpmn-moddle
```

Причина выбора:

* не нужно писать BPMN-парсер вручную;
* `bpmn-moddle` десериализует BPMN XML в объектную модель;
* TypeScript удобен для быстрого локального CLI;
* результат легко сериализовать в JSON;
* нет привязки к Kotlin/JVM.

---

## Важное ограничение

Нельзя просто делать:

```ts
JSON.stringify(definitions)
```

или сериализовать всю BPMN object model как есть.

Нужно сделать выборочную проекцию:

```text
BPMN XML
  → bpmn-moddle object model
  → semantic and execution projection
  → compact JSON
```

Агент должен сам определить, какие поля BPMN object model стоит перенести в compact JSON, исходя из цели: сохранить смысл процесса, технически значимые детали реализации и удалить шум.

---

## Runtime-ограничения

На этапе `BPMN XML → JSON` нельзя использовать LLM для принятия решений.

Конвертер должен быть:

* локальным;
* детерминированным;
* воспроизводимым;
* без сетевых вызовов;
* без недетерминированной логики.

При одинаковом входном BPMN XML должен получаться одинаковый JSON.

LLM-агент может использоваться для разработки, анализа, приемки и написания кода, но не должен быть частью runtime-конвертации BPMN XML в JSON.

---

## Что считать полезной информацией

В JSON должна попадать информация, которая помогает понять:

* из каких элементов состоит процесс;
* как элементы связаны между собой;
* где процесс начинается и заканчивается;
* какие действия выполняются;
* какие есть развилки и условия переходов;
* какие события влияют на ход процесса;
* какие участники, дорожки или роли участвуют в процессе;
* какая документация или текстовые описания есть в BPMN;
* какие подпроцессы, вызовы, сообщения или данные участвуют в процессе;
* как технически реализованы исполняемые элементы процесса;
* какие атрибуты исполнения важны для анализа процесса.

Важно: техническая реализация не считается шумом сама по себе.

Если элемент BPMN содержит информацию о том, как он исполняется, эта информация должна рассматриваться как потенциально полезная.

Примеры потенциально полезной технической информации:

* реализация service task;
* delegate/class/expression/topic;
* called element у call activity;
* script у script task;
* business rule / decision reference у business rule task;
* timer/message/signal/error definitions;
* input/output mappings;
* listeners;
* assignee/candidate groups;
* form key;
* extension elements, если они влияют на исполнение или понимание процесса.

Конкретный набор полей агент определяет самостоятельно на основе BPMN object model и цели конвертера.

---

## Что нужно игнорировать

В JSON не должна попадать информация, которая относится только к визуальному отображению диаграммы или к XML-служебному шуму.

Игнорировать:

* BPMNDiagram;
* BPMNPlane;
* BPMNShape;
* BPMNEdge;
* Bounds;
* waypoint;
* BPMNLabel coordinates;
* координаты;
* размеры;
* layout;
* diagram id;
* shape id;
* edge id;
* XML namespace-шум;
* schemaLocation;
* данные, нужные только BPMN-редактору для отрисовки диаграммы.

Важно: технические данные исполнения не являются layout-шумом.

Например, реализация service task или настройки call activity должны сохраняться, если они есть в BPMN object model и помогают понять поведение процесса.

---

## Требования к выходному JSON

JSON должен быть:

* компактным;
* пригодным для чтения агентом;
* пригодным для последующего преобразования в Markdown;
* не похожим на механическую сериализацию XML;
* без визуального layout-мусора;
* без XML-многословности;
* без данных, нужных только BPMN-редактору;
* со стабильной структурой;
* детерминированным при повторных запусках;
* достаточно полным, чтобы по нему можно было понять не только ход процесса, но и технически значимые детали реализации.

Агент сам проектирует структуру JSON, но она должна отражать BPMN-процесс как исполняемую модель: элементы, связи, условия, события, роли, документацию и важные execution-related детали.

---

## Правила сериализации

JSON должен быть стабильным и компактным.

Рекомендуемые правила:

1. Использовать стабильный порядок элементов.
2. Не выводить поля со значением `undefined`.
3. Не выводить пустые строки.
4. Не выводить бессмысленные пустые структуры.
5. Не выводить `null`, если поле можно просто опустить.
6. Не переносить служебные объекты BPMN-модели целиком.
7. Не допускать циклических ссылок.
8. Не включать технические поля библиотеки, если они не несут смысла для понимания процесса или исполнения.
9. Не включать layout-информацию.
10. Не включать XML namespace-шум.

---

## CLI-интерфейс

Минимальная команда:

```bash
bpmn-to-json input.bpmn -o output.json
```

Допустимо на первом этапе:

```bash
npx tsx src/cli.ts input.bpmn -o output.json
```

CLI должен:

1. Принять путь к входному BPMN/XML-файлу.
2. Принять путь к выходному JSON-файлу через `-o` / `--output`.
3. Прочитать файл.
4. Сконвертировать его.
5. Записать pretty JSON.
6. Завершиться с ошибкой, если файл не читается или BPMN не парсится.

## Предлагаемая минимальная структура проекта

```text
bpmn-json/
  package.json
  tsconfig.json
  src/
    cli.ts
    convert.ts
```

Не нужно делать сложную архитектуру.

### `cli.ts`

Отвечает за:

```text
- чтение аргументов;
- чтение входного файла;
- вызов функции конвертации;
- запись output.json;
- вывод ошибок.
```

### `convert.ts`

Отвечает за:

```text
- создание BpmnModdle;
- вызов moddle.fromXML;
- обход BPMN object model;
- projection BPMN model → compact JSON;
- stable sorting;
- удаление layout-информации;
- удаление undefined/пустых/бесполезных полей.
```

---

## Что не делать в первой версии

Не делать:

```text
автотесты
golden-file tests
полную поддержку BPMN 2.0
профили minimal/business/execution
поддержку всех vendor-specific extensions
JSON Schema
сложную валидацию
batch mode
топологическую сортировку
визуализацию графа
Markdown generation
RAG indexing
```

Если что-то из этого хочется добавить, сначала завершить базовый converter.

Главный приоритет первой версии — работающий вертикальный срез:

```text
input.bpmn → output.json
```

## Ручная приемка агентом

Автотесты не пишем. Полное ручное покрытие не делаем.

После реализации агент должен выполнить smoke-приемку.

### Проверить на 2–3 BPMN-файлах

Минимум:

```text
1. простой линейный процесс:
   startEvent → task → endEvent

2. процесс с развилкой:
   startEvent → task → gateway → task A / task B → endEvent

3. реальный BPMN-файл, если доступен
```

---

## Критерии приемки

MVP считается принятым, если выполнены критерии ниже.

### 1. Конвертер запускается локально

Команда вида:

```bash
bpmn-to-json input.bpmn -o output.json
```

или:

```bash
npx tsx src/cli.ts input.bpmn -o output.json
```

создает `output.json`.

---

### 2. Output является валидным JSON

Проверить:

```bash
cat output.json | jq .
```

или любым другим способом.

---

### 3. JSON содержит структуру процесса

В JSON должна быть видна структура процесса:

```text
- процессы или процесс;
- элементы процесса;
- связи между элементами;
- развилки;
- события;
- задачи;
- завершения процесса.
```

Конкретные имена полей не фиксируются. Главное — чтобы структура была понятна и пригодна для следующего этапа `JSON → Markdown`.

---

### 4. JSON содержит технически значимую информацию

Если в BPMN есть информация о технической реализации исполняемых элементов, она не должна быть бездумно потеряна.

Агент должен проверить, что в JSON сохраняется существенная информация о реализации процесса, если она есть в исходном BPMN.

Примеры:

```text
- реализация service task;
- script у script task;
- called element у call activity;
- decision/business rule details;
- event definitions;
- execution-related extension elements;
- input/output mappings;
- listeners;
- assignee/candidate groups/forms, если они есть и доступны через модель.
```

Конкретный набор полей не фиксируется. Важно, чтобы технически значимая информация не отбрасывалась только потому, что она техническая.

---

### 5. В JSON не попала визуальная информация

В output JSON не должно быть строк:

```text
BPMNDiagram
BPMNPlane
BPMNShape
BPMNEdge
Bounds
waypoint
bpmndi
dc:
di:
width
height
```

---

### 6. JSON не является механической сериализацией XML

Агент должен проверить, что output JSON:

```text
- не содержит весь XML в JSON-форме;
- не содержит служебную структуру BPMN-редактора;
- не содержит циклических/вложенных объектов без необходимости;
- выглядит как компактное описание процесса и его реализации.
```

---

### 7. По JSON можно понять процесс и его реализацию

Агент должен проверить глазами, что по JSON можно понять:

```text
- где процесс начинается;
- какие действия выполняются;
- какие есть развилки;
- по каким условиям идут переходы;
- где процесс заканчивается;
- какие элементы связаны между собой;
- какие элементы являются пользовательскими, сервисными, скриптовыми, rule-based или вызывающими подпроцессы;
- как технически реализованы исполняемые элементы, если такая информация есть в BPMN;
- какие extension/configuration details были сохранены как значимые.
```

---

### 8. Вывод детерминированный

Запустить конвертацию дважды:

```bash
bpmn-to-json input.bpmn -o output-1.json
bpmn-to-json input.bpmn -o output-2.json
diff output-1.json output-2.json
```

`diff` должен быть пустым.

```markdown
# Приемка BPMN XML → JSON converter

Команда выполнена успешно / неуспешно.

## JSON

Output является валидным JSON.

## Структура процесса

## Техническая реализация

## Layout-информация

## Детерминированность

## Замечания

- ...

## Решение

MVP принят / не принят.
```

## Definition of Done

Проект считается завершенным в рамках первой версии, если:

```text
1. Есть локальный CLI-конвертер.
2. Он принимает BPMN XML-файл.
3. Он создает compact JSON.
4. JSON отражает структуру процесса.
5. JSON сохраняет логику процесса.
6. JSON сохраняет технически значимые детали реализации процесса.
7. JSON не является механической сериализацией всего XML.
8. BPMNDI/layout-информация не попадает в JSON.
9. XML-многословность и служебный шум не попадают в JSON.
10. Вывод детерминированный.
11. Агент провел smoke-приемку и написал отчет.
```

## Главный принцип разработки

Не делать лишнего.

Сначала нужен работающий вертикальный срез:

```text
input.bpmn → output.json
```

Если появляется спорный вопрос, выбирать более простой вариант, который быстрее приводит к рабочему продукту.

Приоритеты:

```text
1. Работает локально.
2. Не падает на простом BPMN.
3. Дает полезный JSON.
4. Сохраняет технически значимые детали.
5. Удаляет layout-мусор.
6. Детерминированный вывод.
7. Минимум лишней архитектуры.
```
